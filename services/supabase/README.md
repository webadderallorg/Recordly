# Desktop feedback

See [setup status](SETUP.md) for the applied project configuration, verification, and remaining launch work.

Before releasing feedback submission:

1. Apply `migrations/202609230001_feedback.sql`, `migrations/202609230002_feedback_limits.sql`, `migrations/202610030001_feedback_access.sql`, and `migrations/202611220001_feedback_upload_budget.sql` in order. The migration raises the private feedback bucket to 50 MiB (52,428,800 bytes), within Supabase Free's limit. It does not change the project-wide setting or billing plan.
2. Deploy the `submit-feedback` Edge Function from the repository root with the Supabase CLI: `supabase functions deploy submit-feedback --workdir services --project-ref YOUR_PROJECT_REF`. The function explicitly validates the bearer token with `auth.getUser` before parsing or storing feedback. The function configuration disables only the gateway's JWT check, not the function's authentication.
3. Use the project's built-in `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` secrets for the function. For support notifications, set `FEEDBACK_RESEND_API_KEY` in the project's Edge Function secrets using a separate sending-only Resend key scoped to `auth.recordly.dev`. Leave the Supabase Auth SMTP key and settings unchanged. Never put either key in the desktop app or the repository.
4. Before shipping the new client, store the project's base URL (without a trailing slash) in Supabase Vault as `feedback_cleanup_base_url`. Generate a dedicated random cleanup secret and store the same value as Vault `feedback_cleanup_secret` and Edge secret `FEEDBACK_CLEANUP_SECRET`. The scheduled cleanup runs every 15 minutes through the authenticated function. Existing linked files get at least 30 days from the migration before expiration.

The signed-in desktop client accepts up to five nonempty files totaling 50 MiB per report. Older clients and new submissions of up to 10 MiB still use the original multipart endpoint. Larger reports reserve their declared sizes before sending bytes, then upload in bounded 6 MiB chunks through the Edge Function to private Storage. The server checks the final stored sizes before saving the report. Direct client report inserts and Storage uploads are not allowed. The app can retry a large upload from the last stored chunk while the same draft and reservation are available.

The per-account UTC daily budget is 10 attempts, 25 files, and 50 MiB. The shared budget is 1,000 attempts and 100 MiB per UTC day, with a 500 MiB byte budget over the current and previous 30 UTC dates to leave headroom on Free. Failed attempts count, but resuming an existing upload does not reserve it again. When the attachment byte budget is full, text-only feedback can still be saved if the report budget has room.

Feedback is stored in `public.feedback_reports`. After saving, the function sends a notification from `feedback@auth.recordly.dev` to `support@recordly.dev` with only the report ID. Text, diagnostics, account details and files remain in Supabase. Owners can read their own report rows, but the private `feedback-attachments` bucket is only accessible through staff or the upload service. This prevents repeated client downloads from consuming bandwidth.

Feedback notifications have a separate global budget of 50 per UTC day. When exhausted, reports still save without sending email. The notification retries once on network errors and HTTP 5xx responses, using the same idempotency key. If it still fails (or the key is missing), the report remains saved and the Edge Function logs the report ID and failure. To verify deployment, send a clearly labeled synthetic report with a full 50 MiB attachment, interrupt and retry it, then verify stored size and the matching email. A successful app response confirms storage, not delivery.

On submission, the modal captures up to 100 recent renderer warnings/errors (2,000 characters each), browser/platform details, and a timestamp. Common secrets, URLs, emails, and local home paths are redacted. Arbitrary log objects are not serialized. The final JSON is bounded to 290,000 UTF-8 bytes by dropping oldest entries, below the database's 300,000-byte limit. Diagnostics are automatically included; native-process logs are not collected. Attachments are chosen explicitly.

A local demo account can preview the form but cannot submit without a real Supabase session. Failed submissions keep the draft: the message and sentiment persist across app restarts, while attachments stay in memory only. Completed attachment objects expire after 30 days, or after 24 hours if no report references them; report rows and their metadata remain. Supabase handles unfinished resumable upload parts, and the scheduled cleanup removes expired completed files through the Storage API, not by deleting Storage database rows.

Unit tests exercise the server handler with an injected storage/auth backend. `tests/feedback_limits.sql` and `tests/feedback_upload_budget.sql` verify the quotas, permissions, finalization, and cleanup selection in a disposable database with the migrations applied. They roll back their test data. Live Storage uploads and scheduled cleanup must be checked separately before release.

## Access verification

Run `checks/feedback-quota-access.sql` as postgres after all feedback migrations in a disposable Supabase database. It uses an existing user with no feedback usage today and rolls back test data. It checks server insertion, owner reads and cross-user isolation after hardening, server-only quota access, authenticated attachment-upload denial for the feedback bucket, client report write denial, anonymous read denial, and all three daily limits. The older `checks/feedback-access.sql` is only for testing migration 001 in isolation, before migration 002 removes direct client inserts.

Do not put real account IDs, project references, credentials, or operator setup status in this documentation.

## User-triggered error reports

Apply `202610020001_export_error_reports.sql`, `20261023120000_app_error_report_logs.sql`, and `202611070001_export_error_daily_budget.sql` in order before deploying the updated `submit-export-error` function using `services/supabase/config.toml` (`verify_jwt = false`). The existing endpoint accepts legacy export summaries and version 2 application reports. The latter contain the failure, a fixed context category, format, and a diagnostic snapshot bounded to 290,000 UTF-8 bytes. Request and stored JSON limits are 1,000,000 bytes to allow for nested JSON escaping. Clients cannot insert or read reports directly. Configure the existing public URL/publishable key in the desktop build; never expose a service-role key.

**Report error** sends immediately, without a second confirmation or sign-in. Nothing is sent merely because an error occurs. Each button shows sending, confirmed success, or a retryable failure, and prevents repeated clicks while sending. Error notifications remain available until dismissed and keep their existing retry/copy action alongside reporting. Application error pages use the same reporting component as export errors.

Reports include recent renderer warnings/errors, browser/platform metadata, persisted export diagnostics when available, and the displayed failure. Common secrets, emails, URLs, home paths, external-drive paths and temporary paths are redacted before sending; arbitrary console objects are not serialized. Recordings and attachments are not included. Native-process console logs are not collected. The client sends no session Authorization, cookies or referrer, and the function rejects Authorization headers and unexpected report fields. Supabase infrastructure can retain connection metadata separately.

View `public.export_error_reports` through staff/service-role access. Version 1 reports retain their allowlisted export codes and optional self-reported cloud-plan category. Version 2 reports contain redacted error text and logs and use `unknown` for the cloud plan. Creation times are rounded to the hour. The service-only quota reserves at most 20 reports per minute, 200 reports per UTC day, and 16 MiB (16,777,216 bytes) of PostgreSQL `diagnostics::text` per UTC day, globally. Conditional database updates reserve both daily limits atomically; failed inserts consume their reservation. Daily counters contain only the UTC day, attempt count and byte count.

These conservative defaults allow roughly 57 near-290 KB ASCII diagnostic snapshots per day, or up to 200 smaller reports. All callers share the budget, so other callers can exhaust it. Exhaustion returns a retryable `429 REPORT_LIMIT`; reports are never truncated to fit or reported as successful before storage. The byte cap bounds serialized diagnostic content, including JSON escaping, rather than total disk usage: row/index overhead, WAL and infrastructure logs are additional. The existing daily Cron job removes reports older than 30 days and prunes minute/day quota counters; deletion is not continuous and depends on Cron running.

Coordinate the daily-budget migration and function rollout: the migration removes the old no-argument quota RPC and grants only the new `reserve_export_error_quota(report jsonb)` signature to the service role. Apply the migration, then deploy the matching function promptly. An older function during this interval fails closed with `500 SUBMISSION_FAILED`; do not keep the old RPC available as a fallback, since it bypasses the daily budget. No desktop change is needed for this quota update. Run `tests/export_error_reports.sql` in a disposable migrated database to check privileges, storage limits, quota and retention. Handler tests inject the storage backend; browser tests intercept the network request and verify actual log content, retry and confirmed success. These checks do not establish that the live service has been deployed.
